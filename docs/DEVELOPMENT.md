# Разработка RouteGuard

## Границы компонентов

| Каталог в `routeguard/src` | Ответственность                                                                                   |
| -------------------------- | ------------------------------------------------------------------------------------------------- |
| `cmd/routeguard`           | CLI, сборка зависимостей, бюджет Go runtime                                                       |
| `internal/config`          | Разбор UCI сразу в типизированные структуры, идентификаторы профилей, строгие логические значения |
| `internal/sources`         | Ограниченное чтение HTTPS-списков, DNS, исключение синтетических ответов                          |
| `internal/policy`          | Проверка настроек и детерминированный план адресов; без изменения системы                         |
| `internal/nft`             | Текст правил и проверка реального JSON nftables, включая объединённые интервалы                   |
| `internal/platform`        | Внешние команды, устройства, маршруты, cron                                                       |
| `internal/store`           | Версия формата, миграция, ограниченное чтение, атомарная и устойчивая запись                      |
| `internal/app`             | Применение, восстановление, откат, блокировки и результаты операций                               |

Конкретные адаптеры создаются в CLI. Тесты передают зависимости через небольшие интерфейсы; глобальных изменяемых путей и подмены `PATH` в Go-тестах нет. Разделять компоненты следует по обязанностям, а не создавать отдельный пакет для каждой функции.

LuCI разделён на поля формы, статус, операции и представление страницы. `Save & Apply` сохраняет только RouteGuard и ждёт результат своего задания. Обновление адресов работает с последней применённой конфигурацией; откат ставит его на паузу.

## Инварианты

- Новая установка не содержит профилей, WAN, DNS, режима IPv6 или расписания.
- Ошибки конфигурации, загрузки, DNS и проверки nft не заменяют действующую защиту.
- Успешное чтение таблицы не означает исправность: проверяются hooks, приоритеты, политики, правила, WAN и адреса.
- Одна nft-транзакция меняет только `inet routeguard`. При отсутствии изменений сохраняются счётчики.
- Перед изменением ядра записывается и синхронизируется намерение. Восстановление повторяет его до согласованного состояния; откат записывает собственное намерение до изменения ядра.
- Повреждённые/неподдерживаемые файлы состояния не удаляются автоматически.
- Фоновая операция считается принятой только после подтверждения дочернего процесса. Блокировка переживает передачу управления процессу и освобождается ядром при его завершении.

## Проверки

`make check` запускает Go-тесты, `go vet`, проверки форматирования и shell, тесты цепочки сохранения/применения LuCI. Тестовые текстовые документы хранятся в `testdata` и подключаются через `go:embed`. Маленькие скалярные значения и генерируемые наборы адресов остаются в тестовом коде.

Для подмены интерфейсов в unit-тестах используется [Uber GoMock](https://github.com/uber-go/mock). Версия библиотеки и инструмента `mockgen` закреплена в `go.mod`; генератор запускается через `go tool`, отдельная глобальная установка не требуется. После изменения интерфейса выполните `make generate` и включите изменения файлов `mock/*_mock.go` в коммит. CI повторяет генерацию и проверяет, что результат совпадает с сохранёнными файлами.

Ожидания задаются в конкретном сценарии: аргументы и число вызовов проверяются явно, `gomock.InOrder` используется там, где порядок влияет на корректность. `AnyTimes` оставлен только для сопутствующего логирования. Сценарии восстановления используют настоящий файловый store во временном каталоге; моки вводят ошибки и прерывания на нужной границе операции. DNS-тесты, запуск дочернего процесса и интеграционные проверки nftables продолжают выполнять реальные операции.

Моки лежат в подпапках `mock` рядом с файлами, объявляющими интерфейсы. Имя файла повторяет имя исходника с суффиксом `_mock.go`. Для стандартного интерфейса `net/http.RoundTripper` используется `internal/sources/mock/round_tripper_mock.go`. Директивы генерации находятся в `generate_test.go`. GoMock и зависимости генератора нужны при разработке и тестировании; сборка `./cmd/routeguard` для роутера их не включает и по-прежнему поддерживает `GOPROXY=off`.

`make integration TARGET_ARCH=arm64` использует отдельный контейнер и сетевые пространства имён LAN/двух WAN. Проверяются реальная передача пакетов, IPv4/IPv6, оба hooks, исключения, идемпотентность, повреждение таблицы, отказ применения, откат и восстановление. Контейнер получает расширенные права только для создания этих сетей; сеть хоста не используется.

`make resources TARGET_ARCH=arm64` запускает собственные DNS и HTTPS внутри контейнера. Максимальная конфигурация проверяет 8 профилей, 32 WAN, 256 доменов, 4096 адресов, 128 исключений и 4 источника на профиль. Все документы источников создаются локально. Пороги заданы в `tests/resource-budgets.json`; их изменение требует объяснения и новых замеров.

Для x86_64 используется `TARGET_ARCH=amd64`. Тесты Linux не заменяют проверку целевого OpenWrt и интерфейса LuCI в браузере.

## Сборка релиза

Версия Go зафиксирована в `go.mod`, инструменты форматирования — в `package-lock.json`, SDK и его SHA-256 — в `scripts/sdk.env`. Рецепт OpenWrt использует Go из PATH, без загрузки модулей при сборке.

```sh
sh scripts/build-sdk.sh /path/to/sdk /path/to/dist
```

Скрипт используется и в CI. Он собирает оба APK и проверяет размер движка. Публикация разрешена workflow только после успешных unit/UI, сетевых и ресурсных проверок. Сборка из SDK требует Linux x86_64 и зависимостей, перечисленных в `tests/integration/Dockerfile.sdk`.

Движок статически скомпонован, а пакет LuCI содержит JS и shell. Сценарий явно собирает host-инструменты LuCI, затем использует `NO_DEPS=1` для двух собственных пакетов. Это не исключает зависимости из APK: firewall4, сертификаты и LuCI устанавливает apk из репозиториев соответствующего OpenWrt. Пересборка штатных системных пакетов и модулей ядра для этого не нужна.

## Проверка собранных APK

`tests/openwrt/run.sh` проверяет именно релизные APK в отдельном контейнере с файловой системой OpenWrt 25.12.5 mediatek/filogic. Версия и SHA-256 официального образа, состав проверок и размеры пакетов записаны в [results/openwrt-25.12.5.json](results/openwrt-25.12.5.json).

Для подготовки образа контейнера извлеките `sysupgrade-glinet_gl-mt6000/root` из указанного tar-образа прошивки, распакуйте SquashFS инструментом `unsquashfs` и импортируйте tar его содержимого через `docker import --platform linux/arm64 - routeguard-openwrt:local`. SDK содержит `staging_dir/host/bin/unsquashfs4`; распаковку с созданием файлов устройств выполняйте в отдельном контейнере. Сам образ прошивки на устройство записывать не требуется.

На Linux ARM64 либо Docker с поддержкой запуска ARM64:

```sh
docker run --rm --privileged --network=none \
  -v "$PWD:/src:ro" -v "$PWD/build/dist:/packages:ro" -v "$PWD/build:/out" \
  routeguard-openwrt:local sh /src/tests/openwrt/run.sh
```

Проверяются установка и удаление, пустая начальная конфигурация, UCI, штатный nftables, RPC и список сохраняемых при sysupgrade файлов. Контейнер использует ядро Docker; загрузка через procd, браузер LuCI и физический роутер проверяются отдельно по `OPENWRT-TEST.md`.
